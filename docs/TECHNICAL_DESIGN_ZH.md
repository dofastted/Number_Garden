# 数对花园：原生鸿蒙技术架构与 Agent 施工说明

版本 0.1｜2026-10-01｜范围：先完成可运行样本，后扩展发布版。

## 一、架构结论

**推荐：原生鸿蒙应用宿主 + 可内嵌的原生游戏组件 + 独立规则引擎。**

采用 Stage / UIAbility、ArkTS、ArkUI。一个 entry HAP 负责导航、设置、生命周期和平台能力；garden_core HAR 承载纯规则、状态、求解与接口；number_garden HAR 承载棋盘、数字牌、种子卡和游戏界面。宿主把 GardenGameView 放入原生 GamePage，即实现你说的内嵌形态。[1][2][3]

这不是“为了原生而自己造游戏引擎”，也不是“一个网页套原生壳”。最多 36 格、简单选中/消除动效，优先使用可读屏的 ArkUI 组件，Canvas 只承担不拦截点击的连线或少量效果。先验证实际性能，再考虑替换渲染层。

H5/WebView 与 Cocos/XComponent 是可另立 ADR 的备选路线，不作为首版并行工程。若将来使用 H5，只承载本地表现层；状态、保存、身份、隐私和生命周期仍归原生宿主。禁止暴露任意文件、SQL、eval 等通用桥接接口，禁止加载远端游戏代码。[2]

### 模块职责

| 模块 | 负责 | 不负责 |
|---|---|---|
| entry | Stage 启动、原生导航、平台适配、依赖注入、事务存档 | 复制一套游戏规则 |
| garden_core | 校验动作、生成下一状态、撤销、规则求解、端口接口 | ArkUI、数据库、音效、动画 |
| number_garden | 原生格子、种子托盘、交互草稿、解释和视觉反馈 | 直接写数据库、私自决定胜负 |
| content/tools | 开发机生成题库、独立校验、导出回放 | 作为手机里的 Python 服务 |

纯核心不能依赖 UI。TaskPool 求解入口也不能通过 barrel export 间接引入 UI 装饰器；线程间仅传送受控、可序列化的数据。[5]

## 二、先实现什么

样本目标：**12 关经典配对 + 4 关数独数对 + 一个完整美术主题**。12 关经典跨越六段教学机制，使用 sampleOrder 指定样本顺序，不等于把原来 60 关压缩为最终 12 关。

样本需要：原生首页、关卡列表、两种棋盘、提示、撤销、保存恢复、简短教学、设置、结果页、花园阶段奖励。没有服务器、登录业务后台、广告、充值、体力、排行榜、在线关卡编辑器、随机补牌或 3D。

发布版 60 经典 + 12 数独仍是后续内容目标；这次不以数量填充替代关卡质量。

## 三、规则规格冻结

### 经典配对 classic-v1

数字 1—9，0 为空格。两个端点必须不同且非空，满足“相同或和为 10”，并在同一行/列，之间所有格为空。相同数字不一定和为 10，9 与 9 也合法。

消除只改两个位置，不下落、不补牌、不挤列。禁止斜线、拐弯、跨行首尾。清空全部数字才胜利。无效动作不记入已提交动作，不消耗生命或货币。

例如 `1 4 6 9`：先消 4、6，再跨空格消 1、9。对角上两个数虽然和为 10，也不能配。

### 数独数对 sudoku-pair-4-v1

4×4，数字 1—4，2×2 宫。每行、每列、每宫不重复。所有种子卡公开，卡内两数字相同或和为 5。两个目标位置可以不相邻，也可以不同行列，但最终必须同时满足数独约束。

选择卡 → 可交换顺序 → 放第一个预览 → 放第二个预览 → 明确确认 → 原子落子。尚未确认时，不修改棋盘和库存。切后台取消草稿。已知数不可改；撤销恢复两格并返还同一张卡。

不能把“一格单独合法”当成“两格一起合法”：例如同一宫中两个预览 2，各自看空盘可能可放，但组合后冲突，必须阻止确认。

完整规则延续前一份企划。本包只明确实现细节，不把旧概念图中的斜线或假数独盘照搬进程序。

## 四、状态与保存：先防止半盘错误

### 三层状态

LevelDefinition 是经校验的关卡；CommittedState 是真正的棋盘、卡片库存、胜负和撤销栈；UiDraft 是选中格、预览和动画。UiDraft 可以清除，不能被误当成已经保存的落子。

每个动作携带 sessionId、commandId、expectedRevision。规则引擎只返回新的不可变状态与效果事件，不直接播放声音、写库或操作组件。

处理顺序：接收命令 → 校验 → 计算候选 → RDB 事务保存 → 成功后发布状态 → 播放反馈。数字牌选择可立即响应，但不能先宣告落子成功、稍后悄悄保存失败。

本地 RDB 使用平台提供的关系型数据库能力；具体方法及 API 可用级别由 G0 固定的 SDK 确认，不凭记忆伪造接口。[6]

### 三张表足够

sessions 保存完整状态、初始关卡副本、版本与 revision；command_receipts 保存幂等回执；level_progress 保存首次通关。棋盘、卡片、撤销和首次奖励在同一事务内变化。偏好设置只存音量、振动、对比度等，不把两颗种子分开塞进多个 Preferences key。

重复 commandId 且 payload 相同：返回原回执，不重复执行。相同 ID 换 payload：拒绝。新命令 expectedRevision 过期：拒绝。先查重复回执，再查 revision，避免把正常重试误判成错误。

撤销恢复盘面，但 revision 仍增加。重开产生新 sessionId。切后台不是唯一保存时机，每次确认的完整动作都已经提交。进程被杀后只允许恢复到提交前或提交后的完整状态，不能出现“卡没了，但只放进去一格”。

存档保留所用关卡和规则版本。题库升级不静默换掉正在玩的盘；不支持的版本保留原数据并明确提供处理选择，不直接删存档。

## 五、提示与求解

普通动作校验很小，求解放进独立受控并发任务。返回 SOLVED、UNSOLVABLE、BUDGET_EXCEEDED、CANCELLED，不把超时说成无解。初始建议 150ms/25,000 节点，必要时单次重试 750ms/100,000 节点；这是待真机调整的预算，不是已测性能。

每个结果携带 sessionId、levelDigest、revision、requestId，全部吻合才可展示。用户撤销、重开、切关或返回后，旧提示不能覆盖新状态。TaskPool 的取消不当成“保证立即中断 CPU 运算”，必须同时限制搜索预算、丢弃过期结果。[5]

提示针对当前盘面找有后续解的动作，不机械播放最初参考解。数独提示还要考虑现有种子库存。参考答案是 QA 证据，不是永远有效的提示脚本。

**6×6 是 36 格，单个 32 位位掩码不够。**原生使用显式数组及稳定状态键，或经过独立测试的双字位集。必须覆盖索引 31、32、35 和越界。Python 大整数通过，不代表 ArkTS 位运算安全。

## 六、关卡设计与生产

本包已经生成 16 个样本文件。经典每关具有至少一条独立回放成功的清空路径；数独逐关确认唯一解，并检查缺数集合、卡片库存和原子落子回放一致。机器通过不等于难度已签收，所有 humanReview 仍为 pending。

| 样本组 | 对应关卡 | 教什么 |
|---|---|---|
| 1—2 | classic-001/002 | 相同、选中、取消、再配一对 |
| 3—4 | classic-011/012 | 相加为十，与相同配对并存 |
| 5—6 | classic-021/022 | 先消阻挡，再横向/纵向跨空格 |
| 7—8 | classic-031/032 | 两个方向共同观察 |
| 9—10 | classic-041/042 | 有被证明的错误首步，练习撤销 |
| 11—12 | classic-051/052 | 6×6 边界与放松关 |
| 13—16 | sudoku-001…004 | 2、3、4 张种子卡，独立模式教学 |

经典通过反向插入构造保证存在路径，再用独立代码验证路径。允许多个正确消除顺序，不要求唯一动作序列。数独先终盘再挖偶数空格，独立计数唯一解，再将缺数合法分对。不能先随机给卡后发现无法覆盖剩余数字。

题库元数据区分计划难度与实测难度；记录目标知识点、首个观察点、提示、校验、人工记录。求解节点多不自动等于玩家觉得难。发布版还需要结构去重与更多终盘变化；样本共用终盘用于覆盖实现，不冒充商业内容多样性。

第一版编辑工具是 JSON + 本地脚本，足以开始施工。不搭后台。正式导入前运行 schema、语义、证明、内容摘要和唯一 ID 检查。JSON 类型断言不是运行时校验，布尔数、浮点、NaN、错误长度、重复 cardId 都必须拒绝。

## 七、美术规范

主题：奶油陶瓷牌、深色清晰数字、鼠尾草绿强调色、适量花朵奖励。不是婴幼儿玩具，也不是每格一个 3D 模型。数字实时文字绘制，不能烘焙进美术贴图。

资源：一套数字牌组件、8 个操作图标、6 个花园阶段图、可选 6 个短音效与一个轻音乐循环。资产表列清楚尺寸、用途、源文件和来源状态；当前未生成正式图片/音效，不把 planned 写成完成。字体用系统字体或实际取得许可的字体，不向用户打包容器字体。

格子状态至少包括：空格、普通、选中、无效、固定已知数、玩家落子、半透明预览、提示。用描边、字重和符号辅助颜色；不让 1—9 每个数字一个高饱和糖果色。

局内缩小标题和花园装饰，棋盘优先。效果层不接收点击、不遮数字。图标带文字或可访问名称；不要重现旧图里的有限撤销、洗牌、剩余步数角标。

动效建议：选中 80—100ms，消除 160—220ms，花园变化不超过 600ms，结算可立即跳过。减弱动态效果时去掉缩放、位移和抖动；游戏状态不受动画时长影响。

签名包体先以 30MiB 为预算，其中自有媒体控制在 8MiB 内。预算尚未真机测量，不能靠删除必要平台能力来凑数。

## 八、交互与全年龄可用性

首页主入口“继续游戏”，次入口经典/数独章节与设置。游戏画面分为原生顶部栏、常驻一句规则、棋盘、种子区（仅数独）、底部工具区。结算强调下一关，不堆活动。

经典：首次点选高亮，再点第二个数校验；非法保留第一次选中并说明原因；再次点选同格取消。保存期间不排入无界点击队列。没得配时提供撤销/重开/提示，不强迫看广告。

数独：卡片始终可见；当前待放数字突出；换卡或交换顺序时清除预览位置，避免数字偷偷交换落点。两格预览完成后显式“种下这对”；已知数不允许覆盖。返回或切后台丢弃预览，不影响已提交状态。

紧凑六列布局：320vp 宽屏，两侧各 12vp、棋盘两侧各 4vp、格间 4vp，可以得到约 44.7vp 的格子。常用按钮至少 48vp。大字号无法容纳时使用明确的扩展棋盘/可访问滚动方案，不把字体缩小来假装适配。

每格按稳定行列顺序提供读屏描述，如“第 2 行第 3 列，数字 6，已选中”。不把整个棋盘做成一个无法操作的 Canvas。颜色、音效和震动都不能成为唯一信息通道。

全年龄友好是设计目标，不等于承诺所有年龄无指导完成所有题，也不等于自行确定平台适龄评级。

## 九、Agent 施工与验收

OpenSpec 已拆成 5 个变更，每个包含 proposal/design/tasks/specs；有 32 条需求、59 个场景和 40 个待实施任务。不是只写一段“请用 OpenSpec 开发”。当前主 specs 为空，避免把未实现的行为冒充既成事实；完成变更后再同步/归档。[7—11]

G0 原生模板、版本记录、原生页面与测试；G1 经典配对+保存+提示闭环；G2 数独卡片原子闭环；G3 美术、关卡和无障碍；G4 真机、故障与交付。

总 Agent 负责架构和公共接口；关卡、美术可在接口稳定后并行；独立审查 Agent 对照真实代码与证据，不相信前一个 Agent 的口头“完成”。不让多个 Agent 同时修改同一存档/构建文件。

测试分四层：桌面参考测试、原生纯规则测试、原生平台集成测试、真机人工/性能测试。本包已执行第一层及内容验证，其他不能继承“通过”。官方 OpenSpec CLI 因本环境网络失败未运行，本地结构检查不是其替代品。

当前没有鸿蒙 SDK、HAP、真机成功记录，也没有正式美术资产。开发 Agent 必须在真实环境补齐，不编造 API、签名或测试输出。

## 十、接下来最小可验收交付

先用官方模板做一个原生首页，嵌入一个数字棋盘，完整走通“选数 → 合法消除 → 事务保存 → 退出重进 → 撤销恢复”。然后再加数独。完成这个切片的价值高于先把全部页面、美术和 72 关都堆出来。
